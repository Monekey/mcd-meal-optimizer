## 4. 我用你的 Token 实测出的 14 条硬发现（独家）

> 这部分是任何竞品 README 里都没有的 —— 直接调 `https://mcp.mcd.cn` 拿到的真实结果。

### 4.1 工具实数 **35 个**，官方文档只写了 33 个

多出来的两个**未公开工具**（可用于差异化）：

| Tool | 作用 | 限制 |
|---|---|---|
| `query-promotions` | 查询门店**满减/满折**促销规则 | ⚠️ **仅企业团餐场景（beType=6）可用** |
| `query-survey-coupon` | 按订单号查 CSAT 满意度答卷 + 关联奖券核销状态 | 需要 orderId |

### 4.2 菜单真实结构

```
query-meals → { categories[16], meals{code→SKU}, frequent }
```
实测门店（北京建外SOHO A座，`storeCode=1950564`）返回 **116 个 SKU / 16 个分类**。真实分类名（注意含换行符）：

`人气热卖` `精选单人餐` **`麦金卡专享`** `鸡肉汉堡\n/卷` `小食拼盘\n/多人餐` `蘸酱炸鸡` `随心配\n1+1` `巨无霸\n牛鱼肉堡` `安格斯MAX\n厚牛堡` `炸鸡` `大堡口福\n单人餐` `小食甜品\n/其他` `开心乐园` **`500\n大卡套餐`** `麦咖啡™` `饮品`

**两个直接可用的钩子**：
- 「**麦金卡专享**」是一个独立分类，9 个商品 → 卡 ROI 的天然入口
- 麦当劳**自己就有「500 大卡套餐」分类** → 你可以把它扩展成"任意热量目标"，这是官方能力的增强，叙事极顺

### 4.3 麦金卡 ROI 完全可由 MCP 数据算出（关键验证 ✅）

菜单里每个 SKU 带 `discountType`，持卡价商品标记为 **`"麦金卡优惠"`**，并同时给出 `originalPrice`。

实测真实数据：

| 商品 | 原价 | 麦金卡价 | 单次省 |
|---|---:|---:|---:|
| 全明星双人分享餐八件套 | ¥114.5 | ¥49.9 | **¥64.6** |
| 安格斯厚牛堡四件套随心选 | ¥66 | ¥37 | **¥29.0** |
| 龙焰鸡腿堡四件套 | ¥57 | ¥29 | **¥28.0** |
| 人气超值四件套随心选 | ¥57 | ¥28 | **¥29.0** |
| 麦咖啡奶铁/美式任选 | ¥21 | ¥9.9 | **¥11.1** |

→ **"麦金卡 ROI 精算师"不需要任何硬编码，全部可以从 MCP 实时算出来。** 这是真正的护城河。

### 4.4 价格单位是「整数分」

`calculate-price` 返回 `{"productOriginalPrice":4850,"price":4450,"discount":400}` = ¥48.5 / ¥44.5 / ¥4.0。

→ **用整数分做运算，天然没有浮点误差。** 这也是头部竞品都在强调的"数值不进 LLM"的技术基础。

### 4.5 ⚠️ 字段名映射坑（会踩）

- `query-meals` 返回的是 `code`
- `calculate-price` 的入参要的是 **`productCode`**
- 传错不报错，**静默返回 `price: 0` 和空 `productList`** —— 这个坑会浪费你半天

### 4.6 下单流程有一个隐藏必填项

```
query-nearby-stores → storeCode / beCode
        ↓
calculate-price  → 返回 takeWayList：[{code:"eat-in",title:"堂食"}, {code:"take-in-store",title:"外带"}]
        ↓
create-order     → 必传 takeWayCode（从上面 takeWayList 里选）
```
`create-order` 的必填参数：`storeCode` / `orderType` / `beType` / `items` / **`takeWayCode`**。

### 4.7 营养数据够用

`list-nutrition-foods` 返回 **160 个餐品**，字段：`productName, energyKj, energyKcal, protein, fat, carbohydrate, sodium, calcium`。
实测样例：猪柳麦满分 308 kcal、猪柳蛋麦满分 387 kcal、中薯条 289 kcal、大薯条 379 kcal。
→ **"总热量"功能完全可做**，且能得到蛋白质/脂肪/钠/钙，可做四维营养雷达。

### 4.8 ⚠️ MCP 返回是「Markdown 说明 + 内嵌原始数据」混合体，不是纯结构 API

每个响应长这样：

```
# API Response Information
## Response Structure
- **data**: 服务器时间信息 (Type: object)
  - **data.date**: 日期字符串 (yyyy-MM-dd)
...
## Original Response
{"success":true,"code":200,"data":{...}}
```

`query-store-coupons` 这类工具**只返回 Markdown 表格，没有 JSON 行**。

→ **这是最大的工程量**：必须写一层解析器。但也正是这个难度，把"只会调 API 的人"挡在外面 —— **是你的技术亮点，不是负担**。

### 4.9 ⚠️ 返回不稳定，必须做重试

实测 `list-nutrition-foods` 第一次成功返回 160 条，之后同一 session 连续 5 次重试**全部返回空文本**。
→ **任何一次 MCP 调用都必须带重试 + 降级**（本地缓存快照兜底）。

### 4.10 枚举值表（避免传错）

| 参数 | 取值 |
|---|---|
| `beType` | `1` 到店取餐 · `2` 麦乐送到家 · `5` 得来速(DT) · `6` 企业团餐 |
| `orderType` | `1` 到店（含自取+得来速） · `2` 外送（含麦乐送+团餐） |
| `beCode` | 外送 / 得来速 / 团餐**必传**；到店自取**不传** |

### 4.11 券的数据模型

`query-my-coupons` 实测你的账户 **17 张可用券**，字段含：券名、券ID（**同一券ID可对应多个券码**）、券码、有效期、**标签（"到店专用" / "外送专用"）**。
→ 关键设计点：**券有渠道限制**，组合优化时必须把"到店券"和"外送券"分开算，否则算出的最优解在点餐时作废。

### 4.12 `withOrder` 随单购通道存在，但形态待验证

`calculate-price` / `create-order` 都有 `withOrder` 参数：`{cardId, cardType, membershipCode, membershipSpecId}`（就是麦金卡/早餐卡随单购）。
实测当前门店菜单里**所有商品的 `canWithOrder` 都是 `false`**。

→ **待验证**：随单购推荐是否只在"购物车已成立 + 调 calculate-price"时才返回？这决定了"买卡"能否做成一键闭环。

### 4.13 ❌ 团购券不在 MCP 能力范围内 —— 必须砍

MCP 能吃到的券只有 5 类：`available-coupons`（麦麦省可领）、`query-my-coupons`（我的券）、`query-store-coupons`（门店可用）、`auto-bind-coupons`（一键领）、`query-survey-coupon`（CSAT 奖券）。
而**满减/满折规则（`query-promotions`）明确限定「仅企业团餐场景 beType=6 可用」**。

→ **抖音/美团团购券、第三方代金券，MCP 既查不到也核销不了。** 你的"团购券"设想必须从需求里删掉，或降级为"提示用户到店可用"。

### 4.14 ❌ "偏好档案可切换人"在架构上不成立 —— 必须改设计

**MCP Token 绑定的是一个真实麦当劳会员身份。** 一个人一个 Token，Token 决定了能查到谁的券、谁的订单、谁的积分。

所以"切换人"只能有两种形态：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 口味档案（推荐）** | 一个账户下存多份**偏好档案**（昵称/热量目标/预算/忌口/常点），共享同一 Token | 不能替别人真下单，但能做"给爸爸点一份低钠的" |
| **B. 多 Token 托管** | 应用侧存多个 Token，切换账户 | 安全与合规风险大（一个人持有他人凭证），**不建议** |

**建议做大 A**：把"切换人"重新定义为 **"切换点餐档案"**（谁吃、什么目标、什么预算），这仍然很有价值，而且**官方 APP 完全没有这个能力**。

## 5. 关于「AI 推荐」的成本问题 —— 你担心对了一半

### 5.1 先厘清两种"token"

| 名称 | 费用 | 限制 |
|---|---|---|
| **麦当劳 MCP Token** | **完全免费**（申请即得） | 600 次/分钟，超限 429 |
| **LLM Token**（大模型调用） | 这才是真花钱的 | — |

你担心的成本是第二种。

### 5.2 正确的解法：让"AI 推荐"不需要 AI

头部竞品的核心技术主张是 **"数值不进 LLM"**：

```
MCP 负责取真实数据（菜单/券/价格/营养）
本地确定性算法负责全部算术（整数分，无浮点）
LLM 只负责理解意图 + 讲解方案
```

**"智能推荐"本身完全可以不用大模型**：

用多目标评分函数就够了，例如
`score = w₁·(热量偏差⁻¹) + w₂·(蛋白质达标) + w₃·(实付价格⁻¹) + w₄·(券使用收益) + w₅·(口味偏好命中)`

按档案里的权重调参，就能输出**「综合最优 / 极致省钱 / 低卡优选 / 高蛋白优选」**几套方案。

**这样做的好处全是加分项**：
- 零 API 成本
- **可复现、可解释、可回归测试**（评委认可的技术深度）
- 不会像大模型那样算错价格

### 5.3 如果一定要接 LLM

| 场景 | 成本承担方 |
|---|---|
| 在 **WorkBuddy 里跑**（Skill 形态） | 由用户的 WorkBuddy 承担，**你的项目零成本** |
| 做**独立 Web App** | 用户自带 API Key，或只保留确定性推荐 |
| 想做云端托管 | 需要自建 key + 限流 + 计费，**16 天内不要碰** |

**结论：不要让数值依赖 LLM，也不要让"AI 推荐"依赖外部 API —— 这本身就是你最好的技术卖点。**

## 6. 产品方案建议（含必须的取舍）

### 6.1 统一叙事

**「把麦当劳 APP 变成懂你的麦麦点餐官」**

三层能力，一个故事：

| 层 | 能力 | 对应你的想法 |
|---|---|---|
| **省得更多** | 组合优化 + 券 + **麦金卡 ROI** | 省钱组合 ✅ |
| **吃得明白** | 总价 **+ 总热量 + 四维营养**，双目标求解 | 总热量 ✅ |
| **越用越懂你** | 点餐档案 + 消费年报 | 偏好档案 + Wrapped ✅ |

### 6.2 MVP 范围（16 天内的现实版本）

**做（P0）**
1. **点餐档案**（多档案切换，替代"多人切换"）
2. **选品 → 组合优化**：品类选品 + 券（区分到店/外送）+ 麦金卡价，输出**价格与热量双指标**
3. **麦金卡 ROI 精算**（纯数据驱动，数据已实测可拿）
4. **APP 级 UI**：麦乐送 / 到店取餐 双 Tab + 门店选择 + 菜单分类 + 商品详情 + 购物车 + 结算
5. **核价 + 下单闭环**（calculate-price → create-order）

**砍或降级（P1/P2）**
- ❌ 团购券（MCP 不支持）
- ⏸ 麦麦年报 Wrapped → **第二期/独立入口**，不变量产

### 6.3 唯一能让你拉开差距的功能

**购物车侧边实时显示「当前组合 vs 最优组合」的价差与热量差，并给一个「优化一下」按钮。**

### 6.4 架构（双形态）

| 形态 | 用途 |
|---|---|
| `docs/demo.html`（单文件自包含 + 内置真实数据快照） | **涨星引擎**：零 Token 可玩、可挂 GitHub Pages、可截图传播。快照已生成：`data/mcd_snapshot.json`（5 家门店 / 116 SKU） |
| `server/`（Node 本地服务代理 MCP） | **真能力**：真实核价与下单 |

> ⚠️ **技术提醒**：MCP 是 Streamable HTTP + SSE，**浏览器不能直连**（CORS + 跨域限制），必须走后端代理。且本地服务版必须用**后端自己的地址**打开（如 `http://127.0.0.1:8790`），用 `file://` 或静态预览面板打开会因为取不到 `/api` 而报错。
