# 常见问答与排错

## 报错：「未找到麦当劳 MCP Token」

去 <https://open.mcd.cn/mcp> 用手机号登录 → 右上角【控制台】→【激活】→ 复制 Token。

拿到后二选一：

1. 环境变量：`export MCD_MCP_TOKEN="你的Token"`
2. 在 WorkBuddy 的【连接器】页启用 `mcd-mcp`（本 Skill 会从 `~/.workbuddy/mcp.json` 自动读取）

**不要把 Token 写进任何仓库文件。**

## 报错：`query-meals 调用失败`

1. 确认 `storeCode` 是真的 —— 先用 `node cli.mjs stores --city 北京` 查一个。
2. 确认门店在营业时间外也可能返回空菜单，换个时间试。
3. MCP 偶发返回空，CLI 已内置重试；如果仍失败，等 10 秒再试一次。

## 核价返回 `¥0.00`

**这是字段映射问题的典型症状**，不是商品不可售。
请检查传给 `calculate-price` 的是不是 `productCode`（而不是 `code`）。

## 「热量待核实」是什么意思

说明这个商品的营养数据在官方接口里查不到（套餐尤其常见，即使做过组成补全仍可能缺失）。

**不要把它当成 0 kcal。** 在回答用户时要如实说明：
「其中 N 项热量待核实」，并且不能说这一单"满足了 ≤X kcal 的约束"。

## 「还能再省」的建议，怎么判断是不是"少买"？

三条铁律：

1. **只做同类替换**：套餐只换套餐，单品只换单品
2. **套餐内容不能变少**：新套餐的组成必须**覆盖**旧套餐的组成
3. 支持「打包」方向：把购物车里多个**单品**打包成**套餐**

反例：把「安格斯厚牛堡四件套 ¥37」换成「巨无霸 ¥25.5」，看着省 ¥11.5，
实际少了薯条和饮料 —— **那是少买，不是省钱**。这类建议必须过滤掉。

## 为什么不能只给"最便宜的那个"

因为价格不是唯一目标。用户可能同时在控热量、控预算、要够蛋白。
本 Skill 输出三条路线（最省 / 最平衡 / 更轻），让用户自己选，而不是替他决定。

## 支持麦乐送（外送）吗

支持，传 `--mode delivery`。但注意外送与到店的**菜单和价格是两套**，
不要用一套的 `storeCode` 去查另一套。

## 能帮用户下单吗

**不能，本 Skill 只做决策。**
`create-order` / `draw-lottery` / `party-order-create` 等写入类工具一律不调用。
下单请用户在麦当劳官方 App 或小程序里完成。
