## 正文

```
最近在参加麦当劳的程序员创意开发大赛，把官方 MCP（mcp.mcd.cn）完整跑了一遍，顺手做了个点餐优化器。
踩到的坑记一下，应该对也在写 MCP client 的人有用。

## 实测发现

**1. 工具数是 35，不是 33**
官方文档列了 33 个，tools/list 实际返回 35。多出来的两个是 query-promotions 和 query-survey-coupon。

**2. query-promotions 有隐藏限定**
文档没提，但它的 description 里明确写着「仅企业团餐 beType=6 可用」。
个人开发者基本用不上 —— 如果你的方案依赖「满减券组合」，这条路是死的。

**3. 有个静默陷阱，我卡了挺久**
query-meals 返回的商品标识字段叫 code，但 calculate-price 要的是 productCode。
传错了**不报错**，直接返回 price: 0。没有任何错误提示，很难定位。

**4. 返回不是纯 JSON**
所有工具返回的都是「API 说明 Markdown + 内嵌一行 {"success":...} 的 JSON」的混合体，
想直接用得先写解析层。
营养表更离谱 —— 是一段用「字面量 \n」分隔的自定义表格格式，160 行挤在一个中文逗号分隔的长串里。

**5. 价格是整数「分」**
calculate-price 返回 4850 = ¥48.50。这点其实挺好的，天生没有浮点误差。

**6. 下单必传 takeWayCode**
取值来自核价返回的 takeWayList（堂食 / 外带），不传会失败。

**7. 营养接口不太稳定**
list-nutrition-foods 第一次调用正常，之后连续 5 次全部返回空。
**没有报错，就是空。** 所以必须做重试 + 本地快照兜底，不能假设一次就能拿到。

**8. 官方只公开了 59% 餐品的热量**
114 个在售 SKU 里只有 67 个能匹配到热量，**所有套餐的热量都没给**。
不过 query-meal-detail 会返回套餐的默认组成，把各组件热量加起来可以自己补全。

## 用它做了什么

麦麦点餐官：输入想吃的品类加约束（预算 / 热量上限），枚举真实组合，
输出「最省 / 最平衡 / 更轻」三条路线，每条都带实付金额和总热量。

另外两块是官方 App 没有的：
- 购物车实时提示「同样内容还能再省多少」，并且只给**内容不变少**的建议
  （套餐只换套餐、单品只换单品、新套餐的组成必须覆盖原组成；也支持把多个单品打包成套餐）
- 麦当劳卡 ROI 精算：从菜单的 discountType="麦金卡优惠" 反推卡价，
  输出「盈亏平衡卡费」—— 低于这个数就值得买，不需要知道卡费本身

有个设计上的坚持：**所有算术都在本地做，大模型不参与计算**。
MCP 返回的数字直接进纯函数。不然 LLM 迟早会把价格算错，而价格算错的产品没人敢用。
```
