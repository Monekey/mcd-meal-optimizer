感谢提供 MCP，接入过程整体很顺。整理几个实测中遇到的问题，供文档参考。

**环境**：门店 storeCode=1950564（北京建外SOHO A座），orderType=1 / beType=1

---

### 1. 工具数量与文档不一致

`tools/list` 实际返回 **35** 个工具，文档中列出的为 33 个。
多出的两个是 `query-promotions` 和 `query-survey-coupon`。

（如果这两个是有意不公开的，忽略这条即可。）

### 2. `query-promotions` 的适用范围

它的 description 中写明「仅企业团餐 beType=6 可用」，但文档里似乎没有提到这一点。
个人开发者如果按文档假设它可用于普通点餐场景，会走一段弯路。建议在文档中标注。

### 3. `code` → `productCode` 的字段映射（影响较大）

`query-meals` 返回的商品标识字段名是 `code`，
但 `calculate-price` 的 `items[].productCode` 需要的是**同一个值**、不同的字段名。

如果直接把 `code` 作为 `productCode` 之外的名字传入（或传错字段），
**接口不报错，直接返回 `price: 0`**。

这一点比较难自查 —— 返回里没有 error 字段，也没有 warning，容易误判为"该商品不可售"。
建议：要么字段名对齐，要么在参数缺失/不匹配时返回一个明确的错误码。

### 4. `list-nutrition-foods` 返回不稳定

首次调用正常返回，之后**连续 5 次调用均返回空内容**（无报错、无 HTTP 错误码）。
间隔重试后才恢复。

目前我在客户端侧做了重试 + 本地快照兜底。想确认下是否有已知的限流或缓存行为。

### 5. `query-meal-detail` 的组成信息很有用，建议文档里提一下

`list-nutrition-foods` 只覆盖单品，套餐匹配不上。
但 `query-meal-detail` 会返回套餐的默认组成，把各组成的热量相加就能补全套餐营养。
这个用法文档里没写，但应该是很多人的刚需（122 个在售 SKU 里只有 53 个能直接匹配到热量，套餐基本都没覆盖）。

---
